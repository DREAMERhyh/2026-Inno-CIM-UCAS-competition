## 三、并行度的真正上限（不是会话数）

1. **GPU 串行**——项目出过三次事故（一次 CUDA OOM、两次 Windows 提交内存耗尽 error 1455）。
   **同一时刻只能有一个训练在跑。** M4 在跑期间，其他会话不得碰 GPU。
2. **台账写入串行**——见上。
3. **产物零覆盖**——新产物一律带 `_v7` / `_s43` / `_s44` / `_smoke` 后缀；跑前核验目标目录不存在。

⇒ 实际可并行的形态是「**一个跑 GPU 的 + 若干做零 GPU 的**」，不是"同时开五个都去训练"。

### 3.4 ⚠ 新增红线：**设备口径也是口径**（2026-09-24 实测）

**本项目的规范数字全部是 CUDA 产物**：`v3_probe_info_death.py` 的原始表、
`task1_simplecnn` 的 59.99 / 28.09，**都是 CUDA**。

实测（同一权重、同一口径、CPU vs CUDA 双向对照）：

| 设备 | α=+0.3 的 head | 与 v3 的差 |
|---|---|---|
| **CUDA** | **27.76** | **0.00（逐位）** |
| CPU | 27.77 | 差 **1 张样本**（0.0125 pp = 1/8000） |

⇒ **`head` 是纯前向的确定性量，但跨设备不逐位相同**（特征张量实测 \|Δ\|max ≈ 4e-3）。

**规则**：**任何要与既有数字并列的结果，必须在同一设备上产出。**
把 CPU 读数混进一张 CUDA 表，与红线 7「跨协议数字不可移植」是**同一类错误**，
只不过混的维度是设备而不是脚本。

**操作细则**：
- 重跑/复算既有产物 → **跟着原产物的设备走**，不要图省事换设备
- 新表内部必须同设备；跨设备的数字只能定性对照，不能并列相减
- **判据写"必须逐位一致"时，先确认设备相同**——否则判据物理上不可满足

## 四·补、自主工人的正确开法（2026-09-24 实测通过）

**用户已明确授权**：可以给工人预先授权，让它们不必逐条确认就能跑命令。

**可用命令**（两条实测都通过，全程零权限提示）：

```bash
# 最小（纯读 + 跑命令）
claude --bg --allowedTools="Bash" "<简报>"

# 完整（工人要写自己的报告）
claude --bg --allowedTools="Bash,Read,Write,Edit,Glob,Grep" "<简报>"
```

**两个必须知道的细节**：

1. **必须用 `=` 号连接**。`--allowedTools` 是可变参数（`<tools...>`），
   写成 `--allowedTools "Bash" "简报"` 会把**简报当成第二个工具名吞掉**，
   会话起来后是空的（`idle — send a prompt to start`）。**实测踩过。**
2. 实测返回：三条 Bash 命令（`pwd` / `ls` / `echo`）连跑 + `Write` 写文件，
   全部免确认，`Worked for 8s · done` / `Cogitated for 6s · done`。

**但授权不等于放开纪律**——领地划分（§二）与红线（§三）仍然逐条有效，
而且**恰恰因为工人现在能自主写文件，领地划分变得更重要**。
派活时必须在简报里写死：**独占写哪些路径、绝对不碰哪些路径**。

**仍然不要做的事**：不要用 `--dangerously-skip-permissions`。
`--allowedTools` 是**枚举授权**（列什么给什么），而后者是**全量绕过**（含权限判定本身）。
用户授权的是前者，不是后者。

## 五、已知的坑（实测所得，别再踩）

| 坑 | 事实 | 应对 |
|---|---|---|
| **`claude --resume` 用短 id 会卡死** | background 会话有两个 ID：`id`（给 `logs`/`stop`）与 `sessionId`（短 id + UUID） | `--resume` **必须用完整 sessionId**，且前提是会话已停止 |
| **`--bg` 会话是单向的** | 我开得出、读得到日志、停得掉，但 `SendMessage` 到不了它 | 简报必须**一次写死**；靠 `--bg --resume <完整sessionId>` 续接追问 |
| **两个版本不一致** | PATH 上的 `claude` 是 npm 版 v2.1.246；VS Code 扩展自带的是 v2.1.280 | 同一批任务固定用一份，不跨版本 |
| **跨会话来消息需要用户批准** | 当两个会话权限模式不同时，接收端会 hold 消息等用户点 | 这是设计如此，不是故障 |
| ⚠ **`--bg` 工人不预授权就会卡死** | 实测：我派出的 M4 工人在执行 `cd *` 时弹出"Do you want to proceed?"，而 headless 后台会话**没有人能点"是"**，于是永久卡住 | **见下方「自主工人的正确开法」——已解决** |
| ⚠ **`--allowedTools` 是可变参数，会吞掉提示词** | `claude --bg --allowedTools "Bash" "提示词"` → **提示词被当成第二个工具名吞掉**，会话起来后是空的（`idle — send a prompt to start`） | **必须用 `=` 号**：`--allowedTools="Bash,Read,..."` |
| 🔴 **`joblib` 的 `n_jobs=-1` 会复现红线 2 的历史事故** | M0c 首次冒烟炸出 `OSError: [WinError 1455] 页面文件太小` + `Error loading torch\lib\cufft64_11.dll`。根因：`LogisticRegression(n_jobs=-1)` 在 20 核机上让 joblib 开 **20 个子进程**，Windows 下每个子进程重新 import `__main__` → 每个加载一整套 torch DLL → 提交内存打爆 | **一律用 `n_jobs=None`（串行）**。这条已写进 M0c 的执行条件。**任何 sklearn/joblib 的多进程默认值在使用前都要检查** |
| **内存余量薄** | 实测：物理 15.7 GB / 可用约 3.7 GB；提交 48.15 GB / 可用约 9.32 GB；页面文件 32.45 GB（峰值 7.41 GB）。读数随负载波动很大（事故当时是 0.9 / 4.9 GB） | 开新任务前先看提交内存；**不要同时开多个吃内存的活** |
| 🔴 **不要在 `.tex` 里混写 markdown 语法** | **本阶段踩过三次**（均 claude-e9 犯）。两种残留的失效方式不同：<br>· **反引号**：LaTeX 里是开引号 → 首次踩时编译报 6 个错（`Missing $ inserted`、`Extra alignment tab`）<br>· **`**加粗**`**：`*` 在文本模式只是普通字符 → **完全不报错，静默渲染成字面的星号**（第三次踩，journal 6 处 + technical-report 1 处） | 编辑 `.tex` **一律只用 LaTeX 宏**（`\textbf{}` / `\texttt{}`）。<br>**但不要靠记性**——手动检查已验证会漏（第三次仍漏 1 处）。<br>⇒ **提交 `paper/` 之前必须跑 `tools/check_papers.py`**（退出码 0 才提交）。它做四件事：扫 markdown 残留 + 编译两遍 + 数错误 + 数未定义引用。 |

### 五·补一、怎么开一个真正脱离会话的长任务（**已实测通过**）

**问题**：`run_in_background` 的 Bash 作业挂在会话进程下，会话一死任务就死。
**我们要的是"会话死了训练还在跑"。**

**实测通过的配方**（2026-09-24 验证）：

1. 写一个 `.bat`（**用绝对路径**，内含 `cd /d` 到仓库）：

```bat
@echo off
cd /d d:\deeplearning_practice\存算一体
set PYTHONIOENCODING=utf-8
D:\anaconda3\envs\pytorch_env\python.exe <训练脚本> <参数...>
D:\anaconda3\envs\pytorch_env\python.exe <下一个训练脚本> <参数...>
```

2. 用 `Start-Process` 启动它：

```bash
powershell -NoProfile -Command "Start-Process -FilePath 'cmd.exe' \
  -ArgumentList '/c','d:\deeplearning_practice\存算一体\<脚本名>.bat' -WindowStyle Hidden"
```

**两个必须知道的细节**（都实测踩过）：

- ⚠ **`-ArgumentList` 里的 bat 路径必须写绝对路径**。写相对路径（即使给了 `-WorkingDirectory`）
  **实测不执行、也不报错**——文件不生成、命令静默失败。
- **日志要重定向到文件**（bat 里用 `>> 日志 2>&1`），否则输出无处可去。
  注意 CMD 重定向 + Python 块缓冲 ⇒ 日志**可能要等缓冲区满才刷出来**；
  想确认存活请看 **GPU 利用率**与**产物目录 mtime**，不要只盯日志。

**验证脱离成功的方法**：启动后另起一条命令查进程——
`Get-CimInstance Win32_Process -Filter "name='python.exe'"` 应能看到训练进程；
**且它与当前会话不在同一进程树里**（会话结束后它仍在）。

**别再做的事**：不要用 `run_in_background` 跑长训练。**它不是"后台"，是"本会话的子进程"。**

## 五·补、上下文管理协议（**总管会话必须自己执行**）

> 立这条的直接原因：**有一次会话上下文占满、压缩失败、整个进程死掉，
> 同时把正在跑的训练链一起带走了**（见 `docs/HANDOFF.md` §2）。
> 总管会话是所有会话的头，**不能因为上下文占满就消失**。

|---|---|
| **压缩自己的上下文** | ❌ **做不到**。`/compact` 是**用户命令**，没有对应的工具可调 |
| **把自己的状态写成交接文档** | ✅ 能。**这是"复活"的手段** |
| **看到自己还剩多少上下文** | ✅ 能。每轮都能读到剩余 token 数 |
| **主动在临界点之前停下并交接** | ✅ 能。**这是必须做的** |

### 协议（总管会话执行）

```
每一轮：
  读一下自己还剩多少 token
  剩余 ≥ 20%          → 正常干活
  剩余 20% ~ 10%      → 立刻更新 docs/HANDOFF.md（快照当前状态）
                        并告诉用户：「我快到线了，请开一个新会话，第一句读 docs/HANDOFF.md」
  剩余 < 10%          → 停止接受新任务，只做交接：写完 HANDOFF.md → 报告 → 结束
```

**交叉评估的会话（工人）也同样适用**，只是它们的产出通常已经落在文件里，
交接成本更低。

### 为什么"交接"比"压缩"稳

- **压缩**只在这一条会话里生效；**会话一旦被杀，压缩也救不回来**（实测发生过）
- **交接文档落在仓库里**——符合本项目一贯的"仓库即记忆"，
  而且**新会话读到的是确定的内容**，不依赖压缩摘要的质量
- ⇒ **默认走交接；要压缩由用户决定**（用户随时可以 `/compact`，那是他的选择）

### 交接文档要写什么（`docs/HANDOFF.md` 的格式）

1. **三十秒状态**：正在跑什么、后台 ID、日志路径
2. **接手第一个动作**：3~4 条可直接粘的命令
3. **刚出的事故**（if any）——不写的话接手者会重踩
4. **在途任务的完整状态**：做到哪、还差几步、预计何时完成
5. **完成清单 / 未开始清单**
6. **最容易踩的几条**（指向坑表，不重复）

**原则：交接文档是快照，长期规则指向 `V7_COORDINATION.md`，不复制。**

### 配套纪律：长任务开跑前先写"怎么接住"

M4 那次之所以有惊无险，是因为**恰好前两次已经跑完、第三次还没存盘**。
换个时间点（比如第三次跑到第 150 个 epoch）就是几小时的损失。

⇒ **开长任务（>1h）之前，先在 `HANDOFF.md` 里写下它的后台 ID、日志路径、产物路径**，
以及"若被杀，从哪一步接着跑"。**这条比任何别的都省事。**
